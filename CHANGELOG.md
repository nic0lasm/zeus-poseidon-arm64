## 1.2 — 2026-10-16

- **Release archive built by the CI.** A `release` workflow builds the application on an Apple Silicon Mac of GitHub as `tools/publish.py release` does (reduced FFmpeg, standalone Python, Release build, local signature, self-test, search for words that must never be published) and attaches both archives to a GitHub release when it is published; on a pull request that touches the release chain, the archive stays an artefact of the run. The README (English and French) presents 1.2 and its figures.
- **Overlay, blends and glyph masks in native code.** The pixel routines that the tenth scenario `rare` reaches for the first time are rewritten in `src/win32/native_blending.cpp`: the overlay that marks a building red on run-length images (`0x00416820`, clipped `0x00416AF0`, `0x00416B90`) and on mirrored building tops (`0x00415B80`, `0x00415D30`, `0x00415C40`), the five clipped or mirrored variants of the alpha-blended image (`0x00414CE0`, `0x00414540`, `0x00414190`, `0x004150B0`, `0x00414910`), and the unclipped glyph mask `0x00416C30`. The sprite dispatcher's fast path now covers blended images, the overlay after compressed images and unclipped glyph masks, `0x005ADF00` keeps the overlay in native code, and the mirrored building top `0x005AE1B0` gets the same fast path. Every call of the thirteen routines is identical (`rare`, and `working-city` for the glyph mask), frames and state identical in the ten scenarios. Left to the original because no scenario reaches them: clipped glyph masks, tint, fixed squares, mirrored keyed copies and the overlay of uncompressed images. Rendering steps 5 to 7, step 4 of the plan.
- **Building sites of composite buildings in native code.** The progress of a site `0x0053ECA0` and the search of a site with a part to serve `0x0053EC10` / `0x0053E740` get fast paths that read the virtual methods of the part classes in their code (steps, weights, finished, flags) and leave to the original any unknown method and any site where a part would be served (method `+0x50`), decided before anything is written. Frames and state identical in the ten scenarios, every call identical; `buildings_spawn_walkers` in `working-city` 8.5 → 5.9 ms, tick 1.69 → 1.60 ms (medians of six runs each). Cycle, second lot.
- **Building scan and spawn clear in native code.** `multi_tile_buildings_update` `0x00534F60`, run every tick, scans the buildings for monuments and does nothing else: a fast path makes the scan on the host and leaves a city with a monument to the original. In `buildings_spawn_walkers`, `0x0040EAD0` clears 864 KB with two `REP STOSD` that the emulator runs entry by entry: a host jump clears them at once. Frames and state identical in the ten scenarios, every call identical; tick of `working-city` 1.77 → 1.59 ms (medians of six runs each). Cycle, first lot.
- **Panel texts and string lookup in native code.** `0x00507BF0`, which finds a string of the text file by walking every string of its group before it, is replaced whole; in the layout of the panel texts `0x004F5300`, two host jumps clear the line buffer and fill a line word by word, with the word measure (`0x004F57A0`, `0x00507F20` for each character) done on the host, so the cost of entering native code is paid once per line instead of once per word; the `@G` images and the drawing of the line stay with the original (`src/win32/native_text.cpp`, `docs/engine/interface.md` §11.1). Frames and state identical in the nine scenarios, 77,281 calls identical call by call; under the deterministic clock `working-city` needs about 14 % less CPU (18.5 s → 15.8 s), `options` and `tutorial` 8 to 10 % less; in real time the difference stays within the noise (about 1 point of a core), as #35 found. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Horsemen and standard bearers in native code.** The handlers `0x004B26B0` and `0x004B1840` get the hoplite's fast path (a soldier holding its place in its group, every call in `working-city`), with the group-target test `0x004E17A0`, the group's direction from its first member `0x004E2480` and the horseman's animation `0x005AF8C0`. Horsemen of groups other than `0x21` and `0x22`, other actions and a soldier walking back stay with the original. Frames and state identical in the nine scenarios, every checked call identical (1 in 4); time over `working-city`: horsemen 61 → 21 ms, standard bearers 45 → 11 ms. Walkers, third lot.
- **Hoplites in native code.** The handler of the hoplites `0x004B31F0`, the costliest walker handler in the large city, gets a fast path for a soldier holding its place in its group (in `working-city`, every one of its 35,992 calls): the prologue shared by the soldiers, `figure_type_value` for index 8, `0x004B17F0`, the soldier's place `0x004B1630` with the road entry of the group's building through the composite helpers of `native_buildings.cpp` (now exported), the view direction and the body image. Other actions and a soldier walking back to its place stay with the original. Frames and state identical in the nine scenarios, every checked call identical (1 in 20); the handler's time over `working-city` falls from 135 ms to 41 ms. Walkers, second lot.
- **Walker loops in native code.** `0x0045A5A0`, which sorts and draws the walkers of a tile, gets a fast path, and step 7 of the second drawing pass, which does the same for the tile and for the two rows behind it, now runs natively when every walker is a case of the native `0x0044FEF0`: the walkers are all checked before anything is written, then sorted and drawn. In the large city of the last tutorial the original no longer takes over at the walkers, and the second pass keeps 97 % of its cells in native code (92.4 % before). Documented in `docs/engine/rendering.md` §11.3. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Window frames in native code.** The frames, highlights and button bars drawn from 16-pixel tiles (`0x0059EE90` titled frame, `0x0059F2A0` plain frame, `0x0059F6E0` highlight, `0x0059ED50` button bar) get fast paths in `src/win32/native_frames.cpp` that compute every tile, check before writing anything that the native sprite dispatcher handles them all, and draw them, or hand the call back. No call is handed back in the nine scenarios; frames and state identical, and every call of the four functions in `options`, `working-city` and `tutorial` identical under `--verify`. CPU time of a run goes from 24.2–25.1 s to 21.5–22.4 s on `working-city` and from 36.3–37.4 s to 32.0–32.6 s on `options` (three alternating runs of `main` and the branch on one cloud machine). The tile layout, the groups and the button bar's length table are documented in `docs/engine/interface.md` §5.3. Step 15 of the interface plan.
- **Terrain in native code, steps 1 to 4.** The random draw (`0x004488C0`), the neighbour count (`0x0049CAE0`), the reserved-point test (`0x00496B50`) and the free-area test of the build tools (`0x004A0DC0`, with the playable-diamond tests `0x00496010` and `0x00496080` inside it) are rewritten in `src/win32/native_terrain.cpp`, the first native code of the simulation: the game state stays identical at every tick of the nine scenarios, and each function passes the call-by-call check. The diamond tests are not intercepted on their own: a call into native code costs about 140 ns, more than their emulated instructions, and intercepting them made `poseidon` 12 % slower. The four neighbourhood pattern tests, which no scenario calls, stay with the original. The key of the shared bench references now ignores the native files' lines in `CMakeLists.txt`, so a branch that adds a native file reuses the references of `main`. Step 6 of the plan.
- **Walkers loop in native code.** `walkers_update` `0x004CC8C0`, the last part of the simulation tick and three quarters of its time in the large city, now runs its loop on the host (`src/win32/native_figures.cpp`): two host jumps, at the top of the loop and at the entry of the timer `0x004CC760`, do everything between two walker handlers (skipping the free records among the 2,000, the link `+0x7C`, the count, both timers and their table); the handlers themselves, the removal of a record and `0x004CC160` stay emulated. Frames and state identical in the nine scenarios, and the whole `.data` section identical at the end of `working-city`; on `working-city` under the deterministic clock a simulation tick goes from 2.49–2.73 ms to 1.85–2.12 ms (three runs of `main` and the branch one after the other on one cloud machine). The next lots, by measured cost, are in `docs/engine/simulation.md` §8. Step 7 of the plan, walkers.
- **Route searches in native code.** The breadth-first searches of the simulation, next in the order of the map of the simulation, are rewritten in `src/win32/native_routes.cpp` as fast paths: `route_search` `0x00502EE0` (cache of the last route, search weighted by the kind of each tile, or the owner's search), the water search `0x00503A60`, the bare-land search `0x00587FB0`, the search to a listed tile `0x00588B20`, the search through buildings `0x00588D30`, and eleven copies of one search that differ only by their mask on the route grid (`0x00588920` and seven copies, `0x0058A4D0`, `0x0058A8C0`). Only the 15 that the scenarios call are replaced. Frames and state identical in the nine scenarios, every call of every target identical; on `working-city` under the deterministic clock a simulation tick goes from 2.68–2.74 ms to 2.38–2.52 ms (two runs of `main` and the branch side by side on one cloud machine), about 10 % less. Step 7 of the plan, second item.
- **Composite buildings in native code.** The helpers of sanctuaries and monuments that the map of the simulation found costliest (42 % of the tick's own time in the large city) are rewritten in `src/win32/native_buildings.cpp`: the composite type test `0x005344A0`, the part class `0x0053C1B0`, the part lists and their sizes (`0x0053C2C0`, `0x0053C330`, `0x00540020`, `0x00540090`), the turned offset `0x00546620`, the part size `0x0053D900`, and through fast paths the entry part `0x0053CC30`, the rectangle of the parts `0x0053CD80` and the nearest road `0x0053F810`. The virtual methods of the part classes are read in their code (all are constants today); any other form hands back to the original. Frames and state identical in the nine scenarios, every target identical call by call; on `working-city` under the deterministic clock a simulation tick goes from 5.3–5.8 ms to 3.1–3.3 ms (two runs of `main` and the branch side by side on one cloud machine), about 40 % less. Step 7 of the plan, first item.
- **Walker sort in native code.** `0x00449B30`, which orders the walkers of a tile from the back to the front before they are drawn (rank by their vertical offset in the tile, then by number; it writes the game state, the order of the list), gets a fast path; since its comparator never returns 0 for two distinct walkers, `std::sort` gives the same order as the game's `qsort`. Documented in `docs/engine/rendering.md` §11.3. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Sanctuaries, monuments and wall towers in the native second pass.** `0x0053E5F0`, called for every part of a sanctuary or monument, goes through the C++ object of the part's class (methods `+0x48`, `+0xF8`, `+0xFC`); in the large city of the last tutorial 52,319 of its 53,150 calls draw nothing, and those are now handled natively (in the second pass, and by a fast path on `0x0053E5F0` itself), the 831 that draw an animated image staying with the original. The two towers of building types `0x81`, `0x91`, `0x92` (`0x0041FD40`, images `0x809` and `0x80F`) are drawn through the native sprite dispatcher. The second pass now keeps 92 % of its cells in native code (84 % before), with no resume after the ambient counters. New file `src/win32/native_sanctuaries.cpp`. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Building animations in native code.** `0x00413380` (the current frame of a tile's animation, kept in the tile's byte at `0x00CB4B08`) and `0x0045D140` (its drawing) get fast paths for their common cases, and the second drawing pass now keeps anchors with an animated image in native code instead of handing them back to the original; `0x0044F320`, which in the nine scenarios never draws (28 million calls, all for building types it does not draw), gets a fast path for those types. Documented in `docs/engine/rendering.md` §11.2. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Bases of buildings in native code.** The bases of 2 to 6 tiles (`0x0043FF10` … `0x00441E50`), drawn diamond by diamond in the order of `formats/sg3.md`, are now handled by the sprite dispatcher's fast path; in the large city of the last tutorial the second drawing pass now keeps 84 % of its cells in native code, and the emulated ground tile `0x00457900` falls from 42,500 to 5,941 calls. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Walkers in native code.** `0x0044FEF0`, which draws one walker (its place in the tile from its direction, step or fine position, its one to three sprites in the order its type and view direction give, and the higher neighbouring tiles marked to be drawn again over it), gets a fast path that decides at entry, without writing anything, whether every sprite is a case of the native dispatcher and no game function it does not rewrite is needed (C++ objects of sanctuaries, the trader's text); `0x0041D3D0` (water life of a tile) gets one for the calls that draw nothing, which is every call outside a Poseidon game. Documented in `docs/engine/rendering.md` §11.3. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Map of the simulation.** `docs/engine/simulation.md` gives the order of a simulation tick, the 51 steps of its cycle and what each part costs: in the large city the tick takes 4.36 ms, 19 % of a core in real time, 81 % of it in the walkers and 42 % of its own time in eight small helpers of composite buildings (sanctuaries, monuments). The tick reaches 778 functions (17.9 % of the code) in the nine scenarios; 537 of the 601 that serve it now have a module (`analysis/simulation.tsv`, `tools/build_symbols.py`), 93 of them newly named. New: `zeus-run --call-graph` and `--time-span`, `tools/simulation_map.py`. Step 5 of the plan.
- **Fast bench on a fresh Linux machine, in one command.** `tools/bench_setup.py` installs the build packages, links the game folder, builds Unicorn 2.1.4 from source when the system only has 2.0.1 (Ubuntu 24.04), builds the project and runs the scenarios; with Unicorn 2.1 the emulator can use non-executable pages and a scenario runs about four times faster on Linux. `tools/check_scenarios.py --references DIR` keeps the references of the pure original in a folder shared between machines, under a key that ignores the native functions, and records only those that are missing. Step 2 of the plan.
- **Plan reviewed.** The roadmap says where the project stands after Phases A and B (76 % of the executable's code still in no module; the last drawing routines bring completeness more than speed; the rare drawing cases cannot be proven by the nine scenarios; the bench is slow to set up and slow on Linux with Unicorn 2.0.1) and gives the next steps in order: finish the rendering in progress, a fast bench on Linux, release 1.2, a tenth scenario for the rare drawing cases, a map of the simulation, terrain as the first simulation subsystem in native code.
- **More pixel routines in native code.** Mirrored run-length images (`0x00415490`, `0x004158E0`, `0x00415680`), the whole-row keyed copy `0x00415F50`, and the ground diamond clipped on the left or right (`0x004377B0`, `0x00438A90`, which draw a fixed half of the diamond, with two copying mistakes of the original kept); the sprite dispatcher's fast path now covers them, and uncompressed images clipped vertically. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Engine counters refreshed after the second drawing pass.** 8 native functions of 4,872, 195 understood; native code does 48.7 % of the game's computation on `working-city` (+ 14.7 % partly native). The share of whole native functions is lower than the 54 % announced before because functions that are only partly native are now counted apart.
- **Second pass of the city drawing in native code.** What stands on each tile (`0x00458170`, from `0x00458792`): ground drawn again, ambient counters, building tops and sloped tops, `0x0044F320` and the animation step when they draw nothing, and the walkers' ring when the lists are empty, through a host jump that hands back to the original mid-cell, with its registers, at the first step it does not handle. The native ground tile `0x00457900` now also draws sloped pieces, tiles with flags `0x4020` and tiles with a building. In the large city of the last tutorial 81 % of the cells of this pass stay in native code; in real time its CPU time per simulation tick falls by about a third, and a small city goes from 37 % to 23 % of a core. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Building tops and clipped run-length images in native code.** `0x004163B0` and `0x004165D0` (a run-length image clipped on the left or on the right) are rewritten whole; the sprite dispatcher's fast path uses them, and `0x005ADF00` (the top of a building, 937 calls per city frame) gets a fast path for every case but the overlay colour. The hidden-row skip `0x004170B0` now keeps the original's partial-register quirk (a run of 128 pixels or more inflates the next count on the same row by 256). Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Equivalence harness.** `zeus-run --state-log` writes a fingerprint of the game state at every simulation tick (the 136 variables the game writes into a saved game, located from a save made by the GOG executable, plus the random generator's tick area and the variables recomputed on load); `tools/check_scenarios.py` now records its references with `--no-native` and compares the state tick by tick as well as the frames. `zeus-run --verify ADDRESS[:END]` runs sampled calls of a game function twice from the same state, native replacements off then on (`Cpu::set_native`), and compares registers and memory, stopping at the first difference. Over the nine scenarios the state is identical at all 13,073 ticks and every native replacement passes (268,312 calls compared); see `docs/equivalence.md` ([#26](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/26)).
- **Interface and texts documented.** `docs/engine/interface.md`: mouse and keyboard from the window procedure to the per-turn edges, the screen switch, the 28- and 40-byte widget tables, the control panel, information, message and tooltip windows, fonts, the glyph table, the word and line layout with its `@` codes, call counts on three scenarios and the ordered list of 22 steps to rewrite; 71 functions named in the code map. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Terrain documented.** `docs/engine/terrain.md` describes the map grids of `Zeus.exe` for a hand-written rewrite: the 228 × 228 grids (terrain flags, altitude, ground images, regrowth, desirability, tree depth, meadows…) with their addresses and save and map blocks, the terrain bits the code confirms, the 51-step cycle that runs the rules, desirability spreading (model values, square and rectangular rings, ±100 clamp), the regrowth of trees, reeds and meadows with grazing and timber mills, and the test that decides whether an area can be built on; every claim carries its address and status, and the page ends with the ordered list of functions to rewrite and their call counts. `analysis/symbols.tsv` names and marks 38 more functions as documented. Part of [#71](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/71).
- **Honest engine counters.** The native share is now measured on `working-city` over the game's own x86 code only (host work excluded, reported apart) and given as time and as code bytes: 54 % (+ 12 % partly native); `tools/coverage.py` computes both. All counters are out of the GOG executable's 4,872 functions (8,397 was the 2.1 edition) (#69).
- **Published adventures (`.pak`) documented.** `formats/pak.md`: a `.set` header followed by copies of the adventure's map files; the editor writes the header twice (`0x0042AD86`) and copies each map through a 500,000-byte field of the adventure object, which explains stale map offsets and the map left in that field. `tools/pakfile.py` reads the 130 `.pak` files of the game (259 maps) and writes them back identical. Part of [#30](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/30).
- **Adventure files (`.set`) documented.** `formats/set.md` describes the 54 fields the editor writes (`0x00425910`), how the reader adapts versions 5 to 26, and what is known of each field (episode texts and scenarios, events, embedded parent-city map, adventure kind); `tools/setfile.py` reads the 28 `.set` files of the game and writes them back identical. Part of [#30](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/30).
- **Maps rewritten byte for byte.** `tools/mapfile.py rewrite` reads the 57 maps of the installations (versions 247 to 321) and writes them back identical, using the save-game compressor; `formats/map.md` gains the map writer and reader of the GOG executable and the meaning of the last field of a table entry. Part of [#30](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/30).
- **Saved games: grids.** `formats/sav.md` ties more of the 228 × 228 grids to the code: building and figure per tile (with the per-tile figure chain), desirability, resource regrowth, grids rebuilt from the view orientation, the variables the game recomputes on load, and value counts for every grid of a large city. Part of [#70](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/70).
- **Saved games read and rewritten byte for byte.** `tools/savefile.py` reads every saved game (versions 235 to 321; 219 files checked) and writes it back identical, including the compressed blocks: its hand-written PKWARE DCL implode reproduces the game's output exactly once it keeps one work structure for the whole file, as the game does (at the end of a stream, implode compares bytes past the data). `samples` makes the test saves with `zeus-run --deterministic` (empty city, tutorial, road, large city), which come out identical from one run to the next. `formats/sav.md` gains the building and figure records as created by the game (`0x00493E70`, `0x004D9FD0`), the random generator, the message list, treasury and population. Part of [#70](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/70).
- **Saved games: block table.** `formats/sav.md` lists the 139 blocks written by the GOG executable (`0x0050E2C0`), each with its address in memory, shape and compression, what is known of its content, and how the reader (`0x0050CB80`) adapts the 138-block files of older versions. Saves use PKWARE DCL implode (zlib is not involved). First step of [#70](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/70).
- **Rendering documented.** `docs/engine/rendering.md` describes the rendering of `Zeus.exe` for a hand-written rewrite: surfaces and presentation, sprite banks, the sprite dispatcher (`0x005ACF50`) and its routine for every image type, clipping, overlays and colour mixing, the isometric projection and the three passes of the city drawing loop (`0x00458170`), with addresses, status (verified or hypothesis) and call counts; it ends with the ordered list of functions left to rewrite.

## 1.1 — 2026-10-14

- **Native ground drawing in the city.** The first pass of the city drawing loop (`0x00458170`), the ground of each tile (`0x00457900`) and the 58 × 30 diamond tile (`0x00435070`) run on the host for their common cases, through a new host jump (`Cpu::add_code_jump`) that hands back to the original code with the same registers and variables for every other case. A small city at the default speed went from 51–60 % to 35 % of a core with the same game speed; the large city of the last tutorial barely changes (85 % to 84 %), its cost being in the second pass and the simulation. The eight scenarios give identical frames.
- **Taller wide modes.** Above 768 lines the control panel is extended with its own texture instead of a black band, the building information window opens at the bottom of the screen, and the world map no longer reads past its image (a band of noise under it). `--wide auto` now adds lines on screens taller than 16:9 (1366 / aspect, up to 1023: 16:10 → 1324×843). New `tall` scenario at 1444×903 ([#23](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/23)).
- **Event messages documented.** `formats/eventmsg.md` describes `Zeus eventmsg.txt` (4,172 phrases looked up by name in a table of the executable, how the game skips unknown words and stops at an inner quote) and `Zeus event message categories.txt`; `tools/eventmsg.py` reads all 11 files of the game and, given the executable, checks every phrase name.
- **Building plans documented.** `formats/layout.md` describes the sanctuary, pyramid and palace plans of `Model/` (piece records, the two lists, how the game's `sscanf` copes with damaged lines); `tools/layout.py` reads all 102 files of the game.
- **First launch with fewer clicks.** The file picker opens in Downloads (no folder-access prompt); a window says the game is being unpacked (about a minute) and closes by itself; with no language pack, the game starts in English without asking (Option still opens the list); dropping the GOG installer on the application icon unpacks it straight away (the bundle now declares `.exe` documents without becoming their default app). A player now does 11 actions instead of 14 ([#55](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/55)).
- **`Model/*.txt` documented.** `formats/model.md` describes the difficulty tables (buildings and houses, figures and enemies, tax sentiment, monster strength) and how the game reads them; `tools/model.py` reads all 63 files of the game and checks them against a re-implementation of the game's own parser.
- **Linux build in CI.** The automated build gains an `ubuntu-latest` job (Unicorn, SDL2 and FFmpeg from apt; build with warnings as errors, `zeus-tests`, `--selftest`). Off macOS, CMake no longer links the Apple frameworks and JPEG backgrounds are decoded by FFmpeg (a few pixels differ from ImageIO, see #38). With Unicorn older than 2.1 (Ubuntu 24.04 ships 2.0.1) the non-executable-page protection is skipped, which is slower but correct. The AppImage and the arm64 job wait for later steps. Part of #25.
- **Download in one click, honest first-launch steps.** The README (English and French) opens with a direct link to `releases/latest/download/Zeus-Poseidon-macos-arm64.zip` (`tools/publish.py release` now also writes the archive under that version-free name, same bytes), gives the exact macOS 15 steps (*Privacy & Security → Open Anyway*; right-click → *Open* no longer works), says where to get the GOG installer from a Mac, and that an Apple Silicon Mac is required ([#55](https://github.com/nic0lasm/zeus-poseidon-arm64/issues/55)).
- **Portable first-launch dialogs.** Application mode now asks its questions through a small interface (`dialogs_macos.cpp` unchanged in behaviour: AppleScript and the Option key; `dialogs_sdl.cpp` elsewhere: SDL message boxes, zenity/kdialog file pickers if installed, command-line questions otherwise). On other systems the support folder is `$XDG_DATA_HOME/Zeus Poseidon`, and `ZEUS_ASK_LANGUAGE=1` asks the language again. Part of #25.
- **zeus-run split by role.** `zeus_run.cpp` becomes `src/tools/zeus_run/`: command line, launch, application mode, dialogs, language packs, diagnostics; no change of behaviour or options.
- **Contact sheet of screenshots.** `tools/contact_sheet.py OUT.bmp COLUMNS SHOT.bmp …` puts several captures, halved, in one grid, to review a scripted run at a glance (standard library only).

- **Counting passes and measuring the game speed without editing code.** `zeus-run --count ADDRESS[,…]` prints how many times execution reached each game address, natively rewritten functions included; `--ticks` prints the simulation ticks per second in real time, pauses left out. Code hooks on the same address now chain instead of replacing each other.
- **Unit tests.** A new `zeus-tests` executable, run by the automated build, tests the host parts that do not need the game: WAV reader, test-script parser, Windows-1252 ↔ UTF-8, case-insensitive file lookup, and the sprite dispatcher's clipping (now in `sprite_clip.h`).

## 1.0.1 — 2026-10-14

The game now runs at its real speed (it ran at two thirds of it since 0.2), with less CPU.

- **The game runs at its real speed.** A simulation tick happens only when a turn of the game's
  loop finds its interval elapsed (22 ms at the default 90 % speed), and the host's fixed 16 ms
  pacing rounded that up to 33 ms: since 0.2 the game ran at two thirds of its speed. The host
  now wakes up when the next tick is due: 45 ticks a second at 90 % instead of 30, on 42 % of a
  core instead of 52 %. Scenarios are unaffected (they run on a virtual clock).
- **Native sprite dispatcher.** The function every sprite goes through runs natively for its two
  common cases (run-length and opaque images, neither clipped sideways nor mirrored, 95 % of
  the calls); every other case falls back to the original code. A large city needs 42 % less
  computing time; frames are identical.
- **A new roadmap.** Four horizons after 1.0 — 1.1 *Cool and quiet*, 1.2 *Every edition*, 2.0
  *Everywhere* (Linux, Intel Macs), 3.0 *Recompiled* (no emulator, the player's copy translated
  on their own machine) — and an exploration of the other City Building Series games. Each step
  has a milestone and an issue on GitHub; the roadmap also looks back on what 1.0 taught.

## 0.9 — 2026-10-14

Release candidate for 1.0, meant to be played and reported on before it gets that number.

- **Lighter.** The host keeps in memory only the game files of 4 MB or less, which the game
  reopens all the time; its large picture files are read once per game and the game keeps them
  itself. A running large city uses about 530 MB instead of 700. Memory stays flat over a
  20-minute session.
- In wide mode the display options read the real size ("1324 x 768 resolution", or
  "Résolution 1324 x 768" in French), as does the help for the F7 key. The game's text files
  are left alone: the host replaces the label in the copy it hands to the game.
- **Starts in under a second.** At launch the game reads its event messages and, for each of
  them, looked up its name in a table of 4,172 entries one comparison at a time: 18 million
  calls, three to four seconds of black window. The host now does that look-up natively. The
  table it produces is identical, in English and in French.
- Documentation brought up to date: what works, what runs natively, what is left.
